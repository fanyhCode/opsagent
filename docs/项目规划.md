# OpsAgent 项目规划

本文档记录项目的关键决策、里程碑与验收标准，避免做到一半跑偏。

## 一、关键决策记录

面试时被问到"为什么这么设计"，答案都来自这张表。

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 项目范围 | 可演示的完整闭环，暂不做微服务 / Prometheus / RabbitMQ | 简历项目的核心是"每一句描述都能演示、能被追问"，写了但讲不清的技术是减分项 |
| 部署形态 | 单机 Ubuntu 虚拟机，平台与被监控环境同机 | 无需额外服务器；全程真实接触 Linux、Docker、日志、进程，简历可写"熟悉 Linux 运维与容器化部署" |
| 被监控对象 | 虚拟机自身 + Docker 模拟服务（mysql / redis / order-service 等） | 可人为制造可控故障（CPU 飙高、容器 OOM、日志报错），便于演示与复现 |
| LLM | DeepSeek（chat 模型） | 模型能力强、成本低、OpenAI 兼容接口，Spring AI 接入简单 |
| Embedding | 本地 bge-small-zh（ONNX） | DeepSeek 未提供 Embedding API；本地部署免额外 Key，且"自己部署向量模型"本身是加分点 |
| 向量库 | pgvector（PostgreSQL 容器） | 知识库规模小（千条以内），pgvector 部署简单、支持 HNSW 索引、运维成本低；Milvus 属于过度设计 |
| 交付物 | 可运行仓库 + 故障演示脚本 + 简历描述 + 面试问答手册 | 面试不仅考代码，还考表达；把讲解材料当成项目的一部分来交付 |

## 三、验收标准

项目完成的判定标准（也是面试演示脚本的骨架）：

1. 在 Ubuntu 虚拟机上执行一条命令即可启动整套平台；
2. 人为制造一次故障（如 order-service CPU 飙高），监控页出现告警；
3. Agent 自动完成多轮工具调用：指标 → 进程 → JVM → 日志 → 知识库检索；
4. 输出包含故障根因、影响范围、风险等级与处置建议的诊断报告；
5. 对中风险操作（如重启容器）弹出人工确认，确认后执行并记录审计；
6. 审计页可回放完整执行链路（工具、参数、耗时、风险等级）。

## 五、开发约定

### 1. 工具分工

| 内容 | 在哪里写 | 在哪里运行 |
| --- | --- | --- |
| 后端 Java 代码 | IntelliJ IDEA 2024.2.6 | IDEA 里点 Run 运行（开发阶段） |
| 前端 Vue3 代码 | Visual Studio Code | VS Code 里 `npm run dev` |
| 数据库 / 缓存 / 模拟被监控服务 | Docker | Ubuntu 虚拟机中的 Docker |
| 最终部署 | Docker Compose | Ubuntu 虚拟机 |

### 2. 代码规范

- 所有类、方法、关键逻辑必须有**中文注释**，说明"这段代码解决什么问题"，而不只是翻译代码字面意思；
- 代码写完必须讲解：每个文件负责什么、关键注解和设计选择的理由；
- 提交信息使用约定式前缀：`feat` / `fix` / `docs` / `refactor` / `chore` / `test`。

### 3. 开发节奏

- 每个小步都要"能跑、能验证"，跑通后再进入下一步；
- 每完成一个阶段，同步更新 `docs/Linux学习笔记.md`，把新用到的 Linux 知识与踩坑记录下来。

### 4. 协作规则（2026-09-13 追加）

- **提交推送前必须先测试**：由我先完成编译检查与接口验证，测试通过后才执行 `git commit` / `git push`；没有测试过的代码不推送。
- **技术选型必须先确认**：凡是没有事先约定过的技术方案（框架、类库、工具、目录结构等），都不擅自决定。做法是：
  1. 先盘点本机已有的工具，能直接用的优先用；
  2. 本机没有的，把可选项、推荐方案和理由列出来，由用户拍板后再写代码。
