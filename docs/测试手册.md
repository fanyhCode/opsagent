# OpsAgent 测试手册

> 目的：明确"什么叫测试通过"。每次提交推送前都按本手册走一遍，测试通过才推送。

## 一、四层测试

| 层次 | 查什么 | 用什么工具 |
| --- | --- | --- |
| 1. 编译检查 | 代码能不能编译通过（语法、依赖、注解） | IDEA 里 Build，或命令行跑 Maven |
| 2. 启动检查 | 应用能否正常启动、能否连上数据库 | IDEA 里 Run |
| 3. 接口验证 | 接口是否返回预期结果，异常情况是否有正确提示 | PowerShell / 浏览器 |
| 4. 数据验证 | 数据是否真的正确落库 | Navicat / 命令行 |

## 二、第 1 层：编译检查

IDEA 里菜单 `Build → Build Project`，或命令行（用 IDEA 自带的 Maven）：

```cmd
cd /d C:\Users\86132\projects\opsagent\backend
```

```cmd
"D:\IntelliJ IDEA 2024.2.6\plugins\maven\lib\maven3\bin\mvn.cmd" compile
```

**正确输出**：最后出现 `[INFO] BUILD SUCCESS`
**错误输出**：出现 `[ERROR]` 与 `BUILD FAILURE`，并指出文件与行号。

## 三、第 2 层：启动检查

IDEA 中运行 `OpsAgentApplication`（绿色三角或 `Shift + F10`）。

**正确输出**：

```text
Tomcat started on port 8080
Started OpsAgentApplication in 3.2 seconds
```

**错误对照表**：

| 报错关键字 | 含义 |
| --- | --- |
| `APPLICATION FAILED TO START` | 启动失败，下方写明原因 |
| `Communications link failure` / `Connection refused` | 连不上数据库（虚拟机没开、容器没启动、IP 变了） |
| `Access denied for user` | 数据库账号或密码不对 |
| ``Table 'opsagent.xxx' doesn't exist`` | 表没建，需要执行建表脚本 |
| `Port 8080 was already in use` | 上次的服务还在运行 |

## 四、第 3 层：接口验证

### 4.0 所有接口的统一返回结构

从本版本起所有接口返回同一个结构：

```json
{"code": 200, "message": "操作成功", "data": { }}
```

`code` 约定：**200 成功**、**400 业务错误**（如用户名已存在）、**401 未登录或令牌失效**、**500 系统异常**。

### 4.1 健康检查（无需登录）

浏览器访问 `http://localhost:8080/api/health`。

**正确输出**：

```json
{"code":200,"message":"操作成功","data":{"status":"UP","service":"opsagent-backend","time":"2026-09-14T..."}}
```

### 4.2 不带令牌访问受保护接口（预期被拒绝）

浏览器访问 `http://localhost:8080/api/servers`。

**正确输出**（HTTP 401）：

```json
{"code":401,"message":"未登录，请先登录","data":null}
```

看到 401 说明拦截器生效了，这是**预期行为**，不是故障。

### 4.3 注册（无需登录）

```powershell
Invoke-RestMethod -Uri "http://localhost:8080/api/auth/register" -Method Post -ContentType "application/json" -Body '{"username":"testuser","password":"test123","nickname":"测试用户"}'
```

**正确输出**：`code=200`、`message=注册成功`，`data` 里有 `id/username/nickname/role`，**没有 password**。

**重复注册同一用户名**：`code=400`、`message=用户名已存在`。

### 4.4 登录并拿到令牌（无需登录）

```powershell
Invoke-RestMethod -Uri "http://localhost:8080/api/auth/login" -Method Post -ContentType "application/json" -Body '{"username":"testuser","password":"test123"}'
```

**正确输出**：`code=200`，`data` 里除了用户信息，还有 **`token`** —— 一长串以 `eyJ` 开头的字符串，这就是 JWT 令牌。

**密码错误**：`code=400`、`message=用户名或密码错误`；用户名不存在时也是同一句提示。

### 4.5 带令牌访问受保护接口（关键演示）

登录拿到令牌，再用它访问受保护接口：

```powershell
$login = Invoke-RestMethod -Uri "http://localhost:8080/api/auth/login" -Method Post -ContentType "application/json" -Body '{"username":"testuser","password":"test123"}'
$token = $login.data.token
Invoke-RestMethod -Uri "http://localhost:8080/api/servers" -Headers @{ Authorization = "Bearer $token" }
```

**正确输出**：`code=200`，`data` 是服务器列表（含 `ubuntu-vm`）。

查看当前登录用户：

```powershell
Invoke-RestMethod -Uri "http://localhost:8080/api/auth/me" -Headers @{ Authorization = "Bearer $token" }
```

**正确输出**：`data` 是 `{id, username, role}`，这些信息由令牌解析而来，没有查数据库。

**模拟伪造令牌**：把签名**中间**的一个字符改掉再访问：

```powershell
$parts = $token.Split('.')
$sig = $parts[2].ToCharArray()
$sig[[int]($sig.Length / 2)] = 'A'
$badToken = $parts[0] + '.' + $parts[1] + '.' + (-join $sig)
Invoke-RestMethod -Uri "http://localhost:8080/api/servers" -Headers @{ Authorization = "Bearer $badToken" }
```

**正确输出**：HTTP 401，`message=登录已过期或令牌无效，请重新登录`。

> 注意一个细节：如果只是在令牌**末尾追加**一个字符，验证可能仍然通过——因为 base64 解码时多余的比特会被忽略，解码出来的签名内容并没有变。所以测篡改必须改**中间**的字符。

**模拟提权**：把载荷里的 `VIEWER` 改成 `ADMIN` 再访问，同样返回 401，因为签名对不上。

这验证了 JWT 的核心价值：**令牌一旦被篡改就验签失败**，服务端不必查库就能拒绝非法请求。

## 五、第 4 层：数据验证

用 Navicat 连接虚拟机数据库（主机 `192.168.169.129`、端口 `3306`、用户 `root`、密码 `opsagent123`），查看 `sys_user` 表：

| 字段 | 期望值 |
| --- | --- |
| username | 刚注册的用户名 |
| password | `$2a$10$` 开头的 60 位字符串（BCrypt 哈希，不是明文） |
| role | 新用户默认 `VIEWER` |
| status | 1 |

也可以在虚拟机里用命令行查：

```bash
docker exec opsagent-mysql mysql --default-character-set=utf8mb4 -uroot -popsagent123 -e "SELECT id, username, role, LEFT(password, 7) AS pwd_prefix FROM opsagent.sys_user;"
```

`pwd_prefix` 应当都是 `$2a$10$`。

## 六、每次提交前的固定动作

1. 第 1 层编译检查通过；
2. 第 2 层启动无报错；
3. 第 3 层相关接口返回符合预期（包括 401、密码错误等异常场景）；
4. 第 4 层数据库里的数据正确；
5. 然后才执行 `git add` / `git commit` / `git push`。

任何一层不通过，先修问题，不推送。
